# ファクトリーのワークフローポリシー

このプロジェクトは Archon の共有 SDLC ワークフローを使用する。以下の要件は、ワークフローに適用するプロジェクト固有の指針である。
各ワークフローのゲートは引き続き適用される。この指針自体が、公開、コメント、マージ、デプロイ、スケジュール変更を許可することはない。

## スコープと初期バックログの作成

`MISSION.md` を全文読むこと。バックログとデリバリーに関するすべての判断は、そこで定めたプロダクトのスコープ、対象外の事項、
厳守する不変条件、人間に委ねられた判断に従う。これらと矛盾する作業は、提案するバックログから外し、矛盾の内容を報告する。

プロダクト文書から開発を始める場合、最初のチケットでは、中核となる実際の利用経路のうち、端から端まで実行して検証できる最小のものを扱う。
このチケットには、ポートのプレースホルダーを含む正確な起動コマンドの引数列（argv）、ヘルスチェックのパス、ビルド識別子を返すパス、
永続状態の保存先パスまたは環境変数、テストコマンド、プルリクエストの CI チェックを必ず明記する。
HTTP アプリは、`FACTORY_RUNTIME_CANDIDATE` が設定されていればその値をビルド識別用のパスで正確に返し、未設定なら自身の Git コミットを返す。
プロジェクトが宣言済みの通常の検証ゲートを再利用する。テストや CI の追加は許容するが、判定基準を緩めてはならない。
既存のコードベースにこの基盤がすでに揃っている場合、最初のチケットは通常のユーザーストーリーとする。

## ファクトリーが管理するワークフロー入力

呼び出し元が値を指定しない場合、ファクトリーは `holdout=.factory/holdout/HOLDOUT.md` を `archon-loop`、`archon-manager`、
`archon-holdouts` に渡す。同様に、プロジェクトの `protected_paths`（`harness/harness.config.json` で定義）を
`archon-loop` と `archon-merge-queue` に渡す。ホールドアウトシナリオを読めるエージェントは
`holdout-verifier` と `holdout-writer` だけであり、`.factory/hooks/holdout_fence.py` が他のすべてのエージェントからのアクセスを拒否する。

## ランタイム検証とレビューの証拠

ランタイム検証およびホールドアウト検証の証拠は、引き渡された候補を実際に動かして取得し、その候補の現在のソースの識別情報と一致していなければならない。
ファクトリーのランタイムホストを使う場合は `factory/RUNTIME_HOST.md` に従う。成果物を引き渡すチェックアウトの想定リビジョンからリソースを準備し、
設定されたヘルスチェックとビルド識別子の検査を必須とする。試行ごとに新しい状態を使い、型付きの結果を証拠として保存する。
必須のランタイム検証またはホールドアウト検証の証拠を、通常のチェックで代用してはならない。

独立レビューの証拠には、PR の現在の HEAD に対する Archon の正式なレポート、実装者から独立した人間が実際に行ったレビュー、
またはプロジェクトの指針で認められた形式による外部の独立レビューレポートを使ってよい。
どの場合も、PR の現在の HEAD を特定し、内容が信頼でき、実装者から独立していることが必要である。
さらに、先に進める状態（ready）であると明示し、進行を妨げる未解決の指摘が一つもないことを要する。
証拠が古い場合、曖昧な場合、または実装者自身の申告だけに基づく場合は、判断を保留する。
