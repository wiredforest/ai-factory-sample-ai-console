# プロジェクトのランタイムホスト

通常のアプリケーション実行環境はファクトリーが管理でき、すべてのワークフローとコーディングエージェントは Archon が管理します。ファクトリーは工程の選択、エージェントの再試行、シナリオの評価、ワークフロー出力を解釈して次の作業を起動すること、マージの承認を行いません。

## フォアグラウンド実行と環境の寿命

```text
factory run archon-verify-runtime --runtime-host /private/runtime.json --input scenario=/private/baseline.json
```

利用側のプログラムは、環境を管理する独立したローカルプロセスを起動します。その接続情報を `FACTORY_RUNTIME_URL` と `FACTORY_RUNTIME_TOKEN` で Archon のネイティブ呼び出し **1 回だけ**に渡し、そのフォアグラウンド実行を待って `finally` で管理プロセスを終了します。パイプでも利用側の突然の終了を検出します。管理プロセスは起動準備とセットアップの待機をキャンセルし、管理下のプロセスツリーを終了し、ソースと状態を置いた一時ディレクトリを削除してから終了します。利用側はこの終了を待ち、後片付けに失敗したらコマンドも失敗とします。

`--runtime-host` は `--detach`、`-d`、`--resume` のいずれとも併用できません。等号で値を渡す形式も同様です。実行を永続管理して終了通知を受ける Archon ネイティブの仕組みとは統合していません。フォアグラウンド実行を一時停止または終了すると、その環境は失われます。新しいフォアグラウンド実行からやり直してください。このオプションを付けない通常のファクトリーコマンドでは、ネイティブの切り離し・再開動作が使えます。フォアグラウンドの呼び出しが戻った後も内部で永続的なバックグラウンド処理を続けるワークフロー構成には、ホストモードを使わないでください。

手動で単独実行する場合も、同じ寿命のルールが適用されます。

```text
python factory/runtime_host.py serve --config /private/runtime.json --connection-file /private/connection.json
```

このプロセスをフォアグラウンドで動かしたまま、Archon を別途ネイティブで呼び出します。プロジェクトのコマンドには、継承した環境変数に代えて `--connection-file /private/connection.json` を渡します。Ctrl+C で中断するかプロセスを終了すると、管理下のアプリを片付けて接続ファイルを削除します。親プロセスが突然終了した場合もアプリを片付けます。その際に接続ファイルが残っても、格納されている認証情報は無効なので削除できます。接続ファイルは排他作成し、Unix ではモード 0600 に設定します。Windows では ACL により運用担当者だけがアクセスできるディレクトリを使ってください。Python のモードビットは Windows の ACL の代わりになりません。接続ファイルはリポジトリや公開成果物の外に置き、トークンをコマンド、シナリオ JSON、レポートに含めないでください。

## 信頼された設定（バージョン 1）

設定は運用担当者が管理する JSON で、管理プロセスが一度だけ読み込みます。次はその例です。

```json
{
  "version": 1,
  "roots": {
    "candidate": {
      "path": "/absolute/private/candidate",
      "binding": ".factory-resource.json"
    }
  },
  "include": ["app.py", "src"],
  "shape": "http",
  "setup": ["{python}", "src/prepare.py"],
  "command": ["{python}", "app.py"],
  "env": {"APP_DATABASE": "{state}/app.sqlite"},
  "health_path": "/health",
  "identity_path": "/build-id",
  "timeout_s": 30,
  "mutations": [
    {"id": "negative", "file": "src/store.py", "find": "unique original", "replace": "changed original"}
  ]
}
```

アプリが必要とするファイルとディレクトリだけを列挙します。パスを解決できるのは、名前で指定したルートの配下に限ります。呼び出し元から任意のパスやコマンドを渡すことはできません。Windows のルートにはドライブ名付きの絶対パスを使います。相対パス、ルートから始まってもドライブが未指定のパス、ルートの外に出るパス、リンクを経由するソースパスは拒否します。取り込み対象パスに `.factory`、`.git`、`.archon`、`.claude`、`.env`、`HOLDOUT.md`、仮想環境、node_modules、バイトコードキャッシュは指定できません。指定したディレクトリの中にこれらがあった場合も、明示的にエラーになります。チェックアウト全体を指定しないでください。そのほか評価器が非公開で使うファイルについても、運用担当者が対象から除く必要があります。

### 候補ルートをデリバリー対象のリビジョンに結び付ける

Archon がデリバリーしようとしているチェックアウトから準備処理を実行します。そのデリバリーで選び、信頼できると確認した完全なリビジョンを渡してください。以前の候補ルートから取得してはいけません。

```text
python factory/runtime_resource.py prepare --config /private/runtime.json --destination /private/candidate --expected-revision <delivered-sha>
```

この Python コマンドはプラットフォームに依存しません。同じランタイム設定から `include` を読み込み、Git を直接呼び出して、許可されたコミット済みのアプリケーションパスだけをアーカイブします。追跡済みの評価器、ホールドアウト、その他のリポジトリファイルも、この一覧の外にあればリソースに入りません。コマンドは元のリビジョン、ツリー、取り込み対象一覧、リソースのダイジェストを自身が管理するルートに記録します。追跡済みのソースに未コミット変更がある場合、指定リビジョンがヘルパー自身のチェックアウトの HEAD と異なる場合、取り込み対象が禁止されている・ルート外に出る・存在しない・リンクを経由する場合は処理を拒否します。出力先の範囲が広すぎる場合や相対パスの場合、自身が作成したものではない既存ディレクトリの場合も拒否します。管理外のディレクトリを削除することはありません。通常の手順では `rm`、`find`、シェルのパイプ、プラットフォーム固有のアーカイブプログラムを使いません。

ヘルパーとワークフローの作業ディレクトリは、同じデリバリー対象の Git チェックアウトに属する必要があります。`--expected-revision` を省いた場合も、古いチェックアウトを指すヘルパーの絶対パスは拒否します。自動実行では信頼できる完全な SHA を渡してください。一致しない値は拒否します。シナリオは使用するスロットを片付けてから、ヘルパーの `start` ラッパーを使います。これによりランタイムへの受け渡し時に、同じデリバリー対象のチェックアウトが自身のリビジョンを渡します。

```json
{
  "environment": {
    "ownership": "external",
    "setup": "python factory/runtime_resource.py prepare --config /private/runtime.json --destination /private/candidate && python factory/runtime_host.py setup --slot baseline --connection-file /private/connection.json",
    "start": "python factory/runtime_resource.py start --slot baseline --root candidate --connection-file /private/connection.json",
    "teardown": "python factory/runtime_host.py teardown --slot baseline --connection-file /private/connection.json",
    "candidate_command": "python factory/runtime_host.py identity --slot baseline --connection-file /private/connection.json"
  }
}
```

これらのコマンドは、デリバリー対象のチェックアウトをワークフローの作業ディレクトリとして実行してください。実行ファイルとスクリプトの絶対パスを安全に使えるのは、スクリプトがその同じチェックアウトに属する場合だけです。古いチェックアウトのヘルパーにフォールバックしてはいけません。ホストは起動のたびにリビジョンとの対応付けを読み直して検査します。準備済みのルートが古い、期待リビジョンとして古いものを明示した、準備済みのバイト列が変わった、のいずれかなら、動作検証に入る前に失敗します。

`setup` は任意で、新しいスナップショットの中で実行します。`command` は必須です。どちらも引数配列（argv）だけを受け取り、リテラルの `{python}`、`{source}`、`{state}`、`{port}` を置換します。対応する実行ファイルは Python と Node だけです。シェルコマンド、バッチファイル、プロバイダーの CLI、環境にたまたま存在する Archon コマンドの指定は失敗します。プロジェクトのスクリプトは、自身のスナップショットまたは状態ディレクトリの中に通常のデータや依存関係を準備できます。設定とスクリプトは信頼されたコードです。プロバイダーのラッパーにしたり、ワークフローを起動したりしないでください。アプリケーションコード全体をソースの取り込み対象に含める必要があります。スナップショット外から読み込む可変のコードは、ここでの同一性確認の対象外です。

アプリに渡すのは最小限の OS 環境と、設定に記載した `env` です。プロバイダーの認証情報、制御用の認証情報、親プロセスの任意の変数は継承しません。HOME と一時ディレクトリは新規の状態ディレクトリを指します。書き込み可能なデータベースとアプリデータにはすべて `{state}` または `FACTORY_RUNTIME_STATE` を使用してください。外部 DB を使う設定のアプリをここで動かしても、その DB が隔離されるわけではありません。新たに外部リソースを用意できるのは、このプロセスとファイルシステムの管理範囲内にプロジェクトが収められる場合だけです。現在はリモート DB、コンテナ、サービス、クラウドリソースに対応していません。

## 共有ノードが使う決定論的なコマンド

次のコマンドは評価を行わず、ワークフローポリシーも含みません。

```text
python factory/runtime_host.py setup --slot baseline
python factory/runtime_host.py start --slot baseline --root candidate --expected-revision <delivered-sha>
python factory/runtime_host.py describe --slot baseline
python factory/runtime_host.py identity --slot baseline
python factory/runtime_host.py teardown --slot baseline
python factory/runtime_host.py start --slot negative --root candidate --expected-revision <delivered-sha> --mutation negative
```

スロット名は運用担当者が英数字、アンダースコア、ハイフンを使って決めます。`start` は毎回、まず指定スロットの以前の環境を片付け、現在の正確なバイト列を新しいディレクトリにコピーします。必要なら、一意に特定できる箇所に設定済みの変異を 1 つだけ適用します。続いてセットアップを実行し、ソースを固定してハッシュを計算し、新しいターゲットと状態を割り当て、設定したコマンドを起動して準備完了まで待ちます。任意の `--expected-source <sha256>` を指定すれば古い入力バイト列を拒否できます。ベースライン、ホールドアウト、不正な形式のレポートを受けての再試行、そのどれでも 2 回目の起動は必ず新しい状態から始まります。リビジョンに結び付けたルートでは `--expected-revision` も必須です。結び付けていない通常のルートでも `--expected-source` は使えますが、どのリビジョンをデリバリーしたかは保証しません。いつコマンドを発行するかは共有ワークフローの構成が決めます。Python にスイートを回すループはありません。並行するケースには別々のスロットを使ってください。この管理プロセスはリクエストを直列に処理します。

`setup` は冪等な後片付けを行う区切りです。環境の準備は `start` の中で原子的に行います。`teardown` も冪等で、ファイルを削除する前に子孫プロセスを終了します。認証済みでも形式が不正なリクエストや処理に失敗したリクエストでは、すべての使用中スロットを片付け、安全側に倒して処理を止めます。コマンド、秘密情報、評価器の内容をエラーに含めず、一般的なエラーだけを返します。未認証のリクエストには、稼働中のアプリに影響を与えず 403 を返します。

`start` と `describe` が返す JSON のフィールドは `version`、`slot`、`candidate`、`source_digest`（セットアップと変異適用後の取り込み対象バイト列のダイジェスト）、`input_digest`（プロジェクトのセットアップ前の取り込み対象バイト列のダイジェスト）、`shape`、`target`、`exit_code`、`snapshot`、`state` です。`identity` は生成側の `candidate_command` 用に候補を識別する文字列だけを出力します。ローカル制御 API は POST の `/setup`、`/start`、`/identity`、`/teardown` を使い、これらの CLI フィールドを JSON で渡して `Authorization: Bearer <private token>` で認証します。`/identity` は型情報を持つ JSON 全体を返します。制御 URL は IPv4 ループバックに限定します。リクエストには上限があり、リダイレクトは拒否します。

PR3227 の外部環境契約に合わせるには、`environment.ownership` に `external` を指定し、setup、start、teardown を上記のコマンドに対応付け、`candidate_command` を `identity --slot <case>` に設定します。Archon が作業ディレクトリを変更する場合、実行ファイルとスクリプトには Bash 用に正しくクォートした絶対パスを使います。コマンドはプロジェクトが信頼する固定文字列です。呼び出し元が渡したテキストをシェル構文に展開してはいけません。リビジョンに結び付けた結果では、`source_revision`、`source_tree`、`resource_digest` を通じた入力の対応付けも行います。生成側の現行の起動ノードはコマンドの出力をログに記録し、検証担当にはターゲットの JSON を返しません。プロジェクトのアサーションデータで `describe --slot <case>` を読み取るよう指示すれば、検証担当がターゲットを特定できます。共有スイート側で型付きデータを直接対応付けることもできます。一時的に割り当てたポートをハードコードしないでください。期待する候補 ID は今回の試行から取得します。実装担当の Git HEAD はターゲットを識別するものではありません。

元の `harness/END-TO-END.md`、`.factory/holdout/HOLDOUT.md`、不具合を定義する JSON はそのままにします。アサーションとケースのメタデータは、データとしてのみ扱う別のプロジェクト用 JSON に変換します。非公開のホールドアウトシナリオ JSON は実装担当のチェックアウトの外に保存し、アプリのスナップショットには含めないでください。ファクトリーは共有の指示を生成しません。
### 評価器を使う前に校正する

ユーザーが実際に行う意味のある操作を中心にアサーションを書きます。ユーザーの操作で空でない値を作成または獲得し、実際の状態遷移を経て、結果の値がゼロでないことと画面に現れる状態を確認します。最終状態を直接書き込んだり、「ページが読み込まれる」だけで合格としたりしてはいけません。一意に特定できる箇所に、その動作を壊す変異を 1 つ設定します。

たとえば、両方の対照ケースで、次の例を製品の公開インターフェースに合わせてください。

```json
{
  "assertions": [
    {
      "id": "earned-value",
      "description": "新しい状態から始め、公開インターフェースを使って実際のユーザーレコードを 1 件作成する。値を獲得できる操作をユーザーとして行い、レコードがちょうど 1 件、表示される値が空でなく、獲得した数値がゼロより大きいことを観察する。データベースに直接書き込んだり、結果となる状態を事前に設定したりしてはいけない。"
    }
  ],
  "environment": {
    "ownership": "external",
    "candidate_command": "python factory/runtime_host.py identity --slot baseline --connection-file /private/connection.json"
  }
}
```

ベースライン用と変異用の安定したスロットを起動し、ホストが返す正確な識別値を記録します。呼び出し元が管理するスイートのマニフェストを `archon-verify-runtime-suite` が受け付ける形式で書きます。

```json
{
  "baseline": "baseline",
  "cases": [
    {"id": "baseline", "scenario": "baseline.json", "candidate": "<baseline identity>", "expected_verdict": "verified"},
    {"id": "relevant-fault", "scenario": "relevant-fault.json", "candidate": "<mutation identity>", "expected_verdict": "failed"}
  ]
}
```

2 つのシナリオから起動済みのそれぞれのスロットを検査し、同じ期待動作を適用します。不具合の説明には、意図して用意した対照ケースであることを明記します。次を実行してください。

```text
python factory/consumer.py run archon-verify-runtime-suite --input manifest=/private/calibration/manifest.json
```

`expectations_passed: true` と `baseline_verified: true` の両方が必要です。ネイティブの戻り値ファイルを自分で作らないでください。これとは別に、ベースラインのシナリオと意図的に異なる `candidate` 入力を指定して `archon-verify-runtime` を実行し、ネイティブの判定が `inconclusive` になることを確認します。固定した版のスイートマニフェストのスキーマが期待値として受け付けるのは `verified` と `failed` だけです。このため、候補の同一性やインフラに関する対照を、第 3 のケースの期待値としてスイート内で正しく表現することはできません。実行できなかったケースを、変異の検出として数えてはいけません。

独立したホールドアウトシナリオは非公開とし、校正の際に変更しないでください。初期セットアップ時と、評価器、アサーション、ランタイムアダプター、同一性を確かめるための契約に実質的な変更を加えた後に、この校正を繰り返します。文章表現だけを編集した後は不要です。

プローブコマンドが実際に出した stdout・stderr と終了ステータスを保存します。その保存ファイルを開き、測定値そのものと候補の識別値が記録されていることを確かめてから、証拠として採用します。Windows では `Start-Transcript` がサブプロセスの出力の代わりにターミナルのプロンプトを記録する場合があります。トランスクリプトが空でないことだけでは、観測できた証明になりません。サブプロセスの出力を直接取得してください。元のツール実行の記録を復元する場合は、出所と元の成果物を保ちます。測定値を作り上げたり、再実行の結果を最初の試行のものとして示したりしてはいけません。

## 同一性の確認と対応する実行形式

HTTP アプリは、環境変数 `FACTORY_RUNTIME_CANDIDATE` の文字列をそのまま返すビルド ID 用のパスを実装する必要があります。ヘルスチェックと同一性確認のエンドポイントは、いずれもリダイレクトなしで 200 を返してください。候補の識別値は、固定したソースのバイト列、解決済みの起動引数配列、環境（この実行固有の状態とターゲットの割り当てを含む）から計算したハッシュです。プローブを実行するたびに、管理下のコマンドが生存していること、ソースが引き続き一致すること、そのターゲットが当該 ID を返すことを確認します。ターゲットが古い、停止済み、または別の対象なら失敗します。この同一性確認はアプリの協力を前提とし、任意の localhost サーバーをこの候補とみなすプロキシではありません。ポート割り当てが競合すると同一性または起動準備の確認に失敗します。ホストが無関係なリスナーを強制終了することはありません。ソースのモード変更（chmod）とハッシュ再計算で変更を検出しますが、同じユーザー権限を持つ攻撃者に対して OS が不変性を保証するストレージではありません。

`cli` と `library` は設定済みの Python または Node の引数配列で、有限時間で終了するものに対応します（ライブラリにはプロジェクトのアダプタースクリプトが必要です）。起動時に一度だけ実行し、完了を待って子孫プロセスを片付け、実際の終了コードと候補との対応付けを返します。ターゲットは null です。同一性確認が証明する対象は、その実行のスナップショットとコマンドです。継続中のサーバーを示すものではなく、終了コードがゼロでもアサーションの成功とは判定しません。対話型 CLI、エージェントが任意に指定するライブラリ呼び出し、状態を保持した再起動には対応しません。秘密情報の誤公開を防ぐため、通常のアプリの stdout・stderr は返しません。プロジェクトのアダプターは結果で返された `state` 配下に測定ファイルを書き込むことができ、teardown までネイティブの検証ツールがそれを参照できます。

Windows では、非公開のワーカーがプロジェクトを実行する前に、コマンドをハンドルを閉じるとプロセスを終了する Job Object に割り当てます。後片付けでは、ジョブ内の実行中プロセスがゼロになるのを待ちます。Unix では別セッションとプロセスグループを使い、最初のコマンドが終了した後でも、後片付け時にグループを終了します。Unix のプロジェクトコマンドは同じセッション内にとどまる必要があります。デーモン化、`setsid` による離脱、サービスマネージャーには対応しません。同じユーザーのエージェントを隔離するファイルシステムサンドボックスではありません。信頼されたスクリプトやアプリが意図してファイルや同一性の保証範囲から外れることは可能です。マシンのシャットダウンや管理プロセス自体の強制終了で一時ファイルが残る場合があります。その場合も Windows のジョブハンドルは閉じられ、アプリは終了します。正常完了、セットアップ・起動の失敗、不正なリクエスト、キャンセル、親プロセスの終了は独立した管理プロセスが処理します。ホストマシン喪失からの復旧や、敵対的なプロセスの封じ込めまで保証するものではありません。

## 変異を検出した証拠

```text
python harness/mutations/run.py score-runtime --result /private/native-return.json --candidate <attempt-identity>
```

このコマンドが読み取るのは共有ランタイムが実際に返した `verified`、`verdict`、`candidate`、`checkout`、`summary` です。候補との対応を確認できた `failed` 判定は CAUGHT、`verified` は ESCAPED と採点します。結果が欠落・矛盾・不一致・判定不能のいずれかなら INCONCLUSIVE のままです。共有エージェントの実行主体の情報と各アサーションの証拠は、ネイティブのスイート成果物に残ります。呼び出し元は信頼できるネイティブの戻り値を渡してください。JSON だけでは署名済みの実行記録になりません。モデルの終了コードや合成した `[PASS]` を変異検出の証拠として扱うことはありません。`score` コマンドの対象は、引き続き渡された通常の検査ログだけです。

リポジトリの検査には `python bin/test_runtime_resource.py`、`python bin/test_runtime_host.py`、`python bin/test_consumer.py`、インストール済みのセルフテスト、`python bin/audit.py`、`python bin/selfcheck-mutations.py` を使います。実際のサブプロセスを使ったフィクスチャではローカルのプロセス管理を検証します。稼働中のプロバイダーに実行を帰属できることや、最終的に互換性を持つソースリビジョンの固定までは確認できません。
